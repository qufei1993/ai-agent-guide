AI Agent 工程全景图

当线上 Agent 陷入死循环、编造错误堆栈，或者未经确认就执行了回滚命令时，真正难定位的往往不是“模型笨不笨”，而是故障出在 Context、RAG、Tool Calling、Harness 还是状态恢复。把一次真实的线上排障任务拆成 6 个工程阶段，每个组件的边界就会立刻清晰。

先别急着上 Agent：3 级架构选型光谱

工程落地中最容易踩的坑，是把本该用 20 行代码写死的流程包装成自主 Agent。Anthropic 在 Building Effective Agents ↗ 中给出的核心建议同样适用于所有团队：始终从最简单的方案开始，只有当任务路径无法提前穷举时，才引入模型自主循环。 一手参考 · Anthropic Engineering

LEVEL 01 · 单次调用
单次 LLM + 结构化输出

输入确定、一步出结果，用 Prompt 约束、JSON Schema 校验和按需检索即可闭环。

典型场景：工单分类、合同字段抽取、单篇摘要。
优势：最低延迟、成本可控、最易回归测试。
LEVEL 02 · 代码编排
确定性 Workflow

多步串行、条件路由或并行汇总，但每一步的流转分支都提前写死在业务代码里。

典型场景：发票 OCR → 规则校验 → 写入 ERP。
优势：路径 100% 可预测、可审计。
LEVEL 03 · 自主循环
自主 Agent Loop

问题开放、步骤无法写死，必须让模型根据工具实时返回的环境反馈动态决定下一步。

典型场景：排查未知线上 500、跨仓修 Bug。
代价：必须配套 Harness 护栏、检查点与轨迹评测。

把一次 2 轮线上排障拆成 6 个工程阶段

假设值班工程师向内部运维 Agent 下达一条指令：“今天 v2.14.2 发布后结账接口开始报 500，查出根因并准备回滚方案。” 这是一个典型的 Level 03 开放式任务：模型必须先查日志拿到证据（Turn 1），再基于证据提出回滚方案并经过护栏审批（Turn 2）。

把这两轮循环的网络包和状态流拆开来看，LLM 在整条链路里只负责一件事：根据当前输入的 Token 序列，推理出下一步该输出文本还是调用工具。其余的取数、查库、鉴权、落盘和熔断，全是确定性代码的工作。

为什么工程上必须把“信息平面”和“执行平面”拆开

Agent 系统里最容易踩的坑，是把两个听起来相近的机制当成同一件事。把所有组件分成两条正交主线，边界就会一目了然：一条管“送进模型的信息质量”，另一条管“模型做出决定后程序怎么安全执行”。

剥掉框架包装，最小 Agent 只有 35 行核心循环

    

      无论底层用哪种编程语言，也不管外层包了什么编排框架，生产级单 Agent 的核心控制流都长成下面这个骨架：组装 Context → 调用 LLM → 经过 Harness 校验 → 执行 Tool → 落盘 Checkpoint，直到模型返回最终结论或触及步数预算。

async function runAgentTask(taskId: string, userGoal: string) {
  // 01 + 02. Context 拼装：只加载必要系统规则、RAG 证据与用户记忆
  const evidence = await retrieveRunbook(userGoal);
  const memory = await loadOnCallPreferences(taskId);
  const messages: Message[] = buildContext({ userGoal, evidence, memory });

  for (let step = 1; step <= MAX_STEPS; step++) {
    // 03. LLM 推理：无状态调用，决定直接回答还是发起工具调用
    const reply = await callModel({ messages, tools: declaredTools });
    messages.push(reply.assistantMessage);

    if (reply.stopReason === "end_turn") {
      await saveCheckpoint(taskId, { step, status: "done", messages });
      return reply.finalText;
    }

    for (const call of reply.toolCalls) {
      // 04. Harness 护栏：校验参数 Schema、权限等级与高危人工审批
      const decision = await harness.check(call, { step, budgetRemaining: MAX_STEPS - step });
      if (!decision.allowed) {
        messages.push(toolError(call.id, decision.reason));
        continue;
      }

      // 05. 工具执行（本地函数或 MCP Server），结果写回下一轮上下文
      const output = await executeTool(call.name, call.args, { idempotencyKey: `${taskId}:${step}:${call.id}` });
      messages.push(toolResult(call.id, truncateForBudget(output)));
    }

    // 06. 状态持久化（检查点）与按需上下文压缩（信息层）
    await saveCheckpoint(taskId, { step, status: "running", messages });
    if (estimateTokens(messages) > COMPACT_THRESHOLD) compactOldTurns(messages);
  }
  throw new Error("Exceeded MAX_STEPS budget");
}
