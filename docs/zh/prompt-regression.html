一、什么叫“输出变差”：别急着上另一个模型打分

AI 工程里的回归测试，本质是把不完全确定的模型当成被测函数：固定输入 + 固定 Prompt + 固定检查规则 = 可比较的实验结果。

很多人一听说“评测”，第一反应就是再找一个更贵的模型当裁判。这当然有用，但顺序错了。工程上应该先把最容易确定、成本最低的硬问题用代码拦住，把变差拆成 4 个可观测维度：

维度 1 · 最硬指标
格式变差

新 Prompt 让模型多包了一层 Markdown 代码块，或者把数值字段 score 输出成了字符串，下游解析直接崩溃。

检查手段：output_config.format + Zod Schema 强约束
维度 2 · 核心业务
内容变差

JSON 格式完全合法，但原本能抓出的 SQL 注入被忽略，模型只泛泛地说“代码风格可以优化”。

检查手段：mustMention 关键词 + issueTypes 分类断言
维度 3 · 体验与克制
风格与边界变差

要求一句话总结却吐出 800 字，或者把一段完全正常的工具函数硬生生审出 3 条“安全风险”。

检查手段：字符上限 + 反例（clean-code）零误报检查
维度 4 · 生产成本
成本变差

Prompt 加长了 600 字规则后，通过率只涨了 2%，但单次调用的输入与输出 Token 成本直接翻倍。

检查手段：记录 usage.input_tokens / output_tokens 与耗时
先猜后验
假如你的代码评审测试集里有 4 条用例，全部都是包含真实 Bug 或安全漏洞的代码。新版 Prompt 在这 4 条用例上拿到了 100% 通过率，能直接放心上线吗？
判断正确：只放有问题输入的测试集，会诱导你不断把 Prompt 改得越来越严厉。结果就是模型连正常代码也强行编造出“安全漏洞”和“性能隐患”。下方实验一可以直接看到真实模型输出。

    二、从失败用例里长出 Prompt 规则
    
    
    
      review-v2.md 里的约束不是拍脑袋写出来的，而是从失败 case 里长出来的。
    
    
    
    
      在上面的实验里，review-v1 面对一段普通的 Intl.NumberFormat 价格格式化函数，硬是编造了三条问题：把未校验的 currency 参数说成“安全漏洞（信息泄露）”，又批评它缺少 JSDoc 注释，最终只给了 72 分。
    
    
    
    
      定位到“过度评审”这个失败模式后，review-v2.md 针对性地增加了三条护栏：
    
    
    
      
      
    1. 明确评审优先级：运行时错误 > 安全风险 > 性能问题 > 可维护性。
      2. 
      
    2. 明确零问题出口：如果代码整体没有明显问题，issues 输出空数组，score 应在 80 到 100 之间。
      3. 
      
    3. 划定安全与性能的判定边界：没有看到外部输入、数据库、文件或网络边界时，不要默认判定为安全漏洞；不要把普通对象创建或格式化函数判定为性能问题。
      4. 
    
    
    
    
      加完规则后重跑同一批 4 条 case，clean-code 通过了（评分 95，issues: []），同时前 3 条故障用例没有出现退步。这就是回归测试的核心价值：修掉一个已知失败模式，并证明没有破坏已有能力。
    
    

    
    三、把断言规则与版本门禁接进工作流
    
    
    
      不要只盯着总通过率。如果一个 P0 高危用例从通过变成失败，即使总通过率看起来没怎么掉，这个版本也必须被门禁拦住。
    
    
    
    
      同时，真实项目里只有“关键词 + 类型 + 分数”还不够，工程上通常会逐步补上两道防线：第一道是输出长度/格式冗余检查（防止模型突然变得极其啰嗦，撑爆界面或预算）；第二道是关键用例多次重复运行（即使 temperature: 0，不同服务端版本仍可能出现轻微波动）。

    四、不要神化最小脚本：5 个工程局限
    
    
    
      自己写几十行 TypeScript 断言能解决 60 分的问题，但它不是完整的评测平台。
    
    
    
      
      
    1. 关键词检查很粗糙：模型可能提到了“SQL 注入”，但给出的修复建议是错的；也可能换了同义词描述同一个风险，导致关键词误杀。
      2. 
      
    2. 分数不是绝对标准：不同 Prompt 对 60 分的定义完全不同，必须配合清晰的评分标准说明使用。
      3. 
      
    3. 单次运行不够稳定：即便设置 temperature: 0，服务端升级或浮点非确定性仍会带来波动，关键用例需要多次重复运行。
      4. 
      
    4. 没有 LLM-as-Judge：对于“解释是否清晰”“建议是否可执行”这类软指标，代码规则很难覆盖，需要另一个模型按 Rubric 打分。
      5. 
      
    5. 没有统计 Token 成本：生产脚本应该把 response.usage.input_tokens 和 output_tokens 写入报告，避免质量涨了 2%、账单翻倍。

    把回归评测放进日常开发闭环
    
    
    
      脚本能跑只是起点，真正有价值的是把它固定成 4 步习惯：改 Prompt 前先跑基线保存报告；改 Prompt 后用同一批 case 重跑对比；线上或手测发现离谱输出时，先把输入加进 cases.json 再动手改 Prompt；每次发布不只看总通过率，还要盯住高优先级用例是否退步。

    完整可运行源码
    
      示例位于仓库 examples/core-methods/prompt-regression/（包含 cases.json、prompts/review-v1.md、prompts/review-v2.md 与 run-eval.ts），使用阿里云百炼 Qwen（支持 output_config.format）可直接运行 npx tsx --env-file=.env examples/core-methods/prompt-regression/run-eval.ts。
    
    

    
    
      Prompt 回归评测本质上是一种工程判断习惯，而不是工具堆砌。测试 case 远比 eval 框架值钱：先有几条真实、带反例的代表性数据，再谈自动化评测才有意义。进入后续的 RAG 知识库与 Agent 实战后，你会看到完全相同的闭环在更大的链路上复现，只不过检查对象从一段 JSON 输出，扩展到了检索召回率、引用忠实度以及工具调用的执行轨迹。
