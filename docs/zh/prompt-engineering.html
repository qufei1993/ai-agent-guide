Prompt Engineering：从会提问到会约束模型

很多人把 Prompt Engineering 理解成“如何和 AI 说话”，但一进工程场景就发现：明明写得很清楚，输出却时好时坏。本质上，Prompt 不是在跟模型聊天，而是在用文字构造上下文，把下一个 Token 的概率分布收拢到你期望的边界内。

30 秒速览 · 本章 3 个核心工程判断
  1. 01 先分清锅该谁背：格式硬约束交给 Schema，外部事实交给 RAG，Prompt 只负责把表达和边界收拢。
  2. 02 Temperature 拉高会放大低概率违规词，长 Prompt 里把关键格式约束放在首尾才能避免被中间稀释。
  3. 03 反话与复杂分类优先用覆盖边界的 Few-shot；用户输入拼进模板必须隔离边界，防止代码围栏闭合注入。

为什么同一个 Prompt 输出会不一样

哪怕一字不改，同一个 Prompt 连续跑 5 次也可能吐出 5 种结果，甚至冲破格式约束。先猜一猜，再在骰子机里把 Temperature 拉高试试。

先猜一下 让模型给耳机起一个“不超过 4 个汉字、不要标点”的名字，用 temperature: 0 和 temperature: 1 各跑 5 次，会发生什么？
抓到关键了。在下面实验台把 Temperature 拉高到 1.0 以上你会看到：低概率的异常候选词（比如带标点或超长英文后缀）一旦被拉高权重，不仅输出不稳定，还会直接破坏格式约束。

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

async function generate(temperature: number) {
  return client.messages.create({
    model: process.env.MODEL!,
    max_tokens: 50,
    temperature,
    system: "只输出一个产品名，不超过 4 个汉字，不要标点，不要解释，不要列多个选项。",
    messages: [{ role: "user", content: "给一款耳机起名：音质出色，但续航只有 3 小时。" }],
  });
}

// 当前实验参数：temperature = 0.0
const response = await generate(0.0);
const textBlock = response.content.find((b) => b.type === "text");
console.log(textBlock?.type === "text" ? textBlock.text : "");

LLM 预测下一个 Token 时是在词表概率分布上采样：Temperature 控制分布陡峭程度，Top-K 限制只从前 K 个候选词里抽，Top-P（核采样） 保留累计概率达到 P 的头部词。工程上，分类、提取与结构化输出建议从 temperature: 0 起步，创意发散再调到 0.7 ~ 1.0；Top-K 和 Top-P 大多数场景保持默认即可。

工程提醒 · 思考模式对采样参数的限制
DeepSeek-V4-Pro 等模型开启思考模式时，temperature、top_p 等采样参数会被忽略。需要测试 Temperature 影响时，应在请求里显式关闭思考模式（thinking: { type: "disabled" }），具体以 DeepSeek 思考模式文档 为准。

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const prompt = `将用户评论分类为：正面、中性、负面。

示例：
评论：“音质很好，性价比高。”
分类：正面

示例：
评论：“产品一般，没什么特别的。”
分类：中性

示例：
评论：“等了两周才到，打开还没电，真是太惊喜了。”
分类：负面

请分类：
评论：“这款耳机音质不错，但续航太差了。”
分类：`;

const response = await client.messages.create({
  model: process.env.MODEL!,
  max_tokens: 20,
  temperature: 0,
  messages: [{ role: "user", content: prompt }],
});
测试题：“我 3 岁时，我的搭档年龄是我的 3 倍。现在我 20 岁，我的搭档多大？”
1. 直接回答 ~12 Tokens
60 岁。（容易被“3 倍”误导，直接用 20 × 3）
耗时最低，但多步计算或逻辑陷阱题极易出错，且看不出哪里算错了。
2. CoT（Prompt 引导） ~78 Tokens
1. 我 3 岁时，搭档是 3 × 3 = 9 岁 2. 年龄差是 9 - 3 = 6 岁 3. 现在我 20 岁，搭档是 20 + 6 = 26 岁 最终答案：26 岁
推理过程写在正文里，计入输出 Token，便于工程师人工排查步骤。
3. 原生 Thinking 模式 双 Block 返回
[thinking / reasoning_content 块] 3 岁时搭档 3×3=9 岁，差值恒定为 6 岁。20+6=26 岁。
[text 块] 26 岁。
解析响应时需用 content.find(b => b.type === "text")，不能硬取 content[0]。

Few-shot 的关键不在例子多，而在质量与边界覆盖：分类任务记得打散顺序，刻意放 1~2 个反话或边界案例。多步推理方面，CoT（Wei et al., 2022、Kojima et al., 2022）通过提示词让步骤出现在正文里；而内置思考模式（如 DeepSeek reasoning_content、Claude thinking 块，见 Claude 扩展思考文档）会返回独立思考块，对这类模型不必机械追加“请一步步思考”。

      Prompt Engineering 是一门知道边界、并在边界内精耕的技术。结构分离、位置效应、正向指令、防注入隔离与版本文档化，这几条用顺手之后就会变成工程直觉。但正如开篇边界急诊室看到的，单靠文本提示无法给输出格式提供 100% 确定性保证。下一章将进入结构化输出实战，使用 Zod 和 JSON Schema 在代码层面为模型输出兜底。
